Midas treasury automation

SpiralWorks / Blueline Active Asia  ·  2017  ·  Under NDA

The problem

Treasury ran on staff logging into bank portals by hand to pull statements and push transfers — slow, error-prone, and hard to audit.

What I built
  • Orchestration service driving statement retrieval and outbound transfers across channels.
  • RPA components covering web, Android and Windows desktop banking clients.
  • A low-level keyboard input driver in C++ for reliable input against legacy applications.
How it works

Treasury operations ran on people. Staff logged into bank portals by hand to pull statements and push transfers — slow, easy to get wrong, and close to impossible to audit after the fact, because the only record was whatever someone remembered to write down.

Midas replaced that with an orchestration service driving the same journeys programmatically across several banking channels. Each bank exposes something different — a web portal, an Android app, a Windows desktop client — so the automation had to cover all three rather than assume an API existed.

That meant Selenium and HTTP clients for web channels, Appium for Android and AutoIt for Windows applications, with session handling and retry logic underneath. A low-level keyboard input driver written in C++ handled legacy clients that would not accept synthesised input reliably any other way. Every run leaves a record, which is the point: an automated transfer you cannot audit is not an improvement.
